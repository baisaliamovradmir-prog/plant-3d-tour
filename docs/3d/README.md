# 3D-тур и интерфейс (ветка `3d`)

## Запуск

Всё запускается в Docker на данных-заглушках, бэкенд не нужен.

Разработка с горячей перезагрузкой — http://localhost:5173:

```bash
docker compose -f docker-compose.3d.yml up tour-dev
```

Продакшен-сборка в nginx — http://localhost:8080:

```bash
docker compose -f docker-compose.3d.yml --profile prod up --build tour
```

Без Docker: `npm --prefix frontend install`, затем `npm --prefix frontend run dev`.

## Вместе с прототипом двойника (ветка `frontend`)

Ветки `3d` и `frontend` не пересекаются по файлам: у Тимура `prototype/`, `scripts/`, `data/`, ТЗ и презентация, у нас `frontend/`, `docs/3d/`, `demo/`. `.gitignore` в обеих ветках одинаковый, поэтому `git merge` проходит без конфликтов (проверено на прототипе 1.1).

После слияния оба фронтенда поднимаются одной командой:

```bash
docker compose -f docker-compose.3d.yml --profile prod --profile twin up --build
```

Двойник — http://localhost:5500, тур — http://localhost:8080. Раздел «3D-тур» в двойнике сам находит тур и передаёт в него расчёт.
Без Docker: тур через `npm --prefix frontend run dev`, прототип — открыть `prototype/index.html` (он найдёт тур на :5173).

По отдельности всё работает как раньше: ветка `3d` — тур, ветка `frontend` — прототип со схемой вместо тура.

## Версия для показа (без Node, Python и Docker)

```bash
node demo/build-demo.mjs
```

Собирает `release/plant-tour-demo.zip`: собранный тур в корне сайта, прототип в `/twin/` и `ZAPUSK.bat`. На любой Windows 10/11 архив распаковывают и дважды щёлкают `ZAPUSK.bat` — откроется двойник с туром во фрейме. Инструкция для докладчика — `demo/README.txt`. Нужны обе ветки в одном дереве.

Адреса:
- `/` — выбор маршрута;
- `/tour/1`, `/tour/2`, `/tour/3` — маршруты для абитуриентов, партнёров и новых сотрудников;
- `/tour` — свободный осмотр;
- `/process/1`, `/case/{id}` — процесс и кейс;
- `/login` — вход и регистрация;
- `/dashboard` — дашборд руководителя (роли «руководитель», «администратор»);
- `/tour?edit=1` — редактор точек (роли «редактор», «администратор»).

## Демо-доступ (режим mock)

Тур открыт без входа. Для остального на странице входа есть кнопки демо-учёток, пароль у всех `demo1234`:

| E-mail | Роль | Куда попадает после входа |
|---|---|---|
| `manager@demo.ru` | руководитель | дашборд |
| `editor@demo.ru` | редактор | тур с редактором точек |
| `admin@demo.ru` | администратор | дашборд, доступен и редактор |
| `visitor@demo.ru` | посетитель | выбор маршрута |

Зарегистрированные в браузере пользователи хранятся в localStorage с хэшем пароля (SHA-256). Права в интерфейсе только скрывают недоступные разделы, окончательно их проверяет сервер (НФТ-5).

## Данные из цифрового двойника

Прототип дашборда (ветка `frontend`, `prototype/`) встраивает тур во `<iframe>` и после каждого прогона модели отправляет результат:

```js
frame.contentWindow.postMessage({
  type: 'plant-twin:run', version: 1,
  scenario: 'параметры прогона с дашборда',
  params:  { demand_tpd, series, setup_pct, seed },
  process: { cycle_h, output_tpd, bottleneck_load_pct, cost_rub_t },
  stages:  { 1: { duration_h, load_pct }, …, 7: { … } },   // id этапа = process_stages.id
}, tourOrigin)
```

Загрузку можно прислать долей (0,96) или процентами (96). Тур принимает только числа, остальное отбрасывает (`parseTwinMessage`).

Что меняется в туре:
- подписи загрузки над зданиями генплана, маяк и очередь партий у узкого места;
- табло этапов в цехах и очередь проб на табло лаборатории;
- показатели в карточке точки с пометкой «из расчёта цифрового двойника»;
- на сцене появляется метка «Данные двойника».

Тур при загрузке сообщает родителю `{ type: 'plant-twin:ready', version: 1 }`, чтобы дашборд мог повторить отправку.

Команда «показать место»: `{ type: 'plant-twin:show', version: 1, stage_id }` (или `location_id` и `hotspot_id`) — тур открывает локацию этапа и его точку интереса. Её шлёт кнопка «Показать в 3D-туре» у узкого места в прототипе. Пример: включите в прототипе второй пост анализа ОТК — узкое место в туре переедет из лаборатории в цех фасовки.

## Для бэкенда (Андрей)

Поля в `src/3d/api/mock/*.json` совпадают с DBML из «Структуры проекта», их можно брать как основу для `seed/demo.json`. Чтобы переключиться на живое API, задайте `VITE_API_MODE=live`.

Сверх таблицы API в документе нужны:
- `GET /api/locations/` — список локаций для генплана и мини-карты;
- `GET /api/enterprise/` — название и описание предприятия для главной;
- `GET /api/cases/` — список кейсов;
- `POST /api/auth/login/` и `POST /api/auth/register/` — ответ `{ token, user: { email, name, role } }`, роль: `visitor`, `manager`, `editor`, `admin`;
- `DELETE /api/auth/me/` — удаление аккаунта (152-ФЗ);
- `GET /api/dashboard/` — формат как у `mock.getDashboard()` в `client.js`: `kpi` (метрики процесса с `series` за 30 дней и `value_30d_ago`), `stages`, `bottleneck` (с `advice`, `case`, `hotspot_id`), `cases`, `views`, `routes` (`starts`, `finishes`);
- в `tour_events.event_type`, кроме `open` и `finish`, нужен `start` — по нему считается, где бросают маршрут.
